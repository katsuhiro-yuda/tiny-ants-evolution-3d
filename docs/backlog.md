# 残課題

各Phaseの完了報告で挙がった、その場では対応しない課題の一覧。
Phase完了時にこのファイルを更新する。MVP対象外の機能要望は書かない（仕様書 §20「将来拡張」へ）。

## 未対応

### バンドルサイズが 1.1 MB（gzip 303 kB）

- 検出: Phase 0 / `npm run build` の警告
- 原因: `three` と `@react-three/drei` が大半を占める
- 影響: 初回ロードが重い。PWAのプリキャッシュ対象になるためPhase 5でより効いてくる
- 対応時期: **Phase 5**（PWA導入時）
- 方針: `drei` を必要なコンポーネントのみに絞る、`build.rolldownOptions.output.codeSplitting` でチャンク分割を検討する。着手前に実測してから判断する

### favicon 未設定

- 検出: Phase 0 / 開発サーバーで `/favicon.ico` が404
- 影響: 機能影響なし。コンソールにエラーが出るだけ
- 対応時期: **Phase 5**（PWAアイコン一式とあわせて作成）

### `noUncheckedIndexedAccess` が無効

- 検出: Phase 0 / `tsconfig.json` の方針決定時
- 判断: 有効にすると配列・TypedArrayの添字アクセスが `T | undefined` になり、シミュレーションのホットループに `!` が増える
- Phase 2 での再検討結果: **無効のまま据え置く**。`survival.ts` の逆順ループ、`AntInstances.tsx` のインスタンス書き込み、`ecotype.ts` のパーセンタイル算出など、添字アクセスが増えたため、有効化すると `!` の数も増える。範囲外参照は単体テストで検出できている
- 対応時期: **据え置き**。Phase 5 の保存・復元で外部由来のデータを扱うときに再検討する（そこは値域検証が必須になるため、型で守る価値が上がる）

### E2Eの速度テストが環境のフレームレートに依存する

- 検出: Phase 1 / E2E導入時
- 内容: ソフトウェアWebGL（SwiftShader）では低フレームレートになり、1フレームあたりのステップ数上限（`MAX_STEPS_PER_FRAME`）に張り付いて4倍速が4倍に届かない
- 影響: 絶対値での判定ができず、等倍との相対比較でしか検証していない。速度倍率の正確さはE2Eでは担保されない（単体テストの `clock.test.ts` で担保）
- Phase 2 での再発: 3部位描画を入れた直後、等倍でも上限に張り付いて相対比較すら成立しなくなった。描画を生存個体ぶんだけに絞って解消したが、描画を重くすると再発しうる
- 対応時期: **対応不要**。判断と再発条件の記録として残す

### `decideBehavior` が意思決定のたびに乱数生成器を生成する

- 検出: Phase 1 / 行動スコアのランダム性修正時
- 内容: 行動ごとに独立したゆらぎを得るため、`context.noise` を種に `createRandom` を呼んでいる。1回の意思決定につきクロージャ4つ分のオブジェクトが確保される
- Phase 2 時点の実測: 100〜280匹で更新時間 0.3〜0.6 ms。GCに起因するコマ落ちは確認できていない
- 対応時期: **500匹規模の計測でGCが問題になった場合**
- 方針: 最適化の前に必ず計測する。必要なら `Random` を再シード可能にするか、生成器を1つ使い回す形へ変える

### 単体テストの実行時間が約60秒に増えた

- 検出: Phase 2 / `evolution.test.ts` 追加時
- 内容: 「50世代以上に到達する」テストはシミュレーション内で2500秒前後（約15万ステップ）進める必要があり、このテストだけで30秒前後かかる。Phase 1 までは全体で4秒だった
- 影響: 開発中の `npm run test` が重くなる。CIでも同様
- 判断: Phase 2 の完了条件そのものを検証するテストのため削除も短縮もしない。個体数を減らせば速くなるが、100匹で調整した餌バランスとは別条件になり、検証の意味が変わる
- 対応時期: **判断待ち**。さらに遅くなるようなら、重いテストにタグを付けて通常実行から外し、Phase完了時とCIでのみ実行する形を検討する

### 500匹規模の性能が未実測

- 検出: Phase 2 / 性能確認時
- 内容: 性能目標は「100匹で60 FPS、500匹で30 FPS以上」（仕様書 §13）。実測できたのは最大282匹までで、そのとき 60 FPS・描画 1.6 ms・更新 0.6 ms だった。個体数上限の500に達する状況を作れていない
- 理由: 現在の餌バランスでは環境収容力が40〜280匹の範囲で振動し、500匹まで増えない
- 対応時期: **Phase 3**（小昆虫と死骸が増えて資源量が変わるタイミング）
- 方針: 餌を増やした設定で上限まで増やし、FPS・描画時間・更新時間を計測する。計測してから最適化する

### 蟻の脚と触角が未実装

- 検出: Phase 2 / 形質の外観反映時
- 内容: 仕様書 §11 は「頭、胸、腹、6本脚、触角を単純形状で表現」としているが、実装したのは頭・胸・腹の3部位まで。speed（脚が長く細い）と visionRange（目・触角）は胸の細長さと頭の大きさで代替している
- 判断: 6本脚と触角を `InstancedMesh` で描くと1匹あたり9〜11インスタンスになり、500匹で最大5500インスタンスになる。性能目標との兼ね合いで見送った
- 対応時期: **Phase 5**（仕上げ）。500匹規模の実測（上記）の結果を見てから判断する

### 体格・視野・繁殖力の見た目の差が小さい

- 検出: Phase 2 / 蟻の色を見直したとき
- 内容: 形質を絶対値（0〜1）で見た目へ写しているが、集団の形質は中央付近に集まるため、実際に使われるのは中央の狭い範囲だけになる。食性の色は集団内で意味のある閾値（`DIET_THRESHOLD`）を基準に正規化して解決したが、以下は絶対値のまま
  - 体色の明度（`longevity`）— 個体間の差は255階調で20程度
  - 全身サイズ（`bodySize`）— 実際に使われるスケールは 0.93〜1.17（±12%）
  - 胸の細長さ（`speed`）、頭の大きさ（`visionRange`）、腹の大きさ（`fertility`）
- 影響: 仕様書 §11「色だけでなく形、サイズ、ラベルでも違いを示す」のうち、形とサイズが機能していない
- 対応時期: **判断待ち**
- 方針: 統計が既に持っている平均・標準偏差・上位20%の閾値を使い、集団内での相対位置で見た目を決める。基準を毎フレーム更新すると見た目がちらつくため、統計スナップショット（250msごと）の値を使う

### 描画層に自動テストがない

- 検出: Phase 2 / 描画の最適化を入れたとき
- 内容: 「毎フレーム容量ぶんを走査せず、生存個体ぶんだけ書き込む」最適化を入れた際、一度も書き込まれないスロットが原点に等倍で描画される不具合が入った（`InstancedMesh` の行列は単位行列で初期化されるため）。画面中央に大きな白い球が出ていたが、typecheck・lint・単体テスト・E2E のいずれも検出せず、目視でのみ発見した
- 影響: 描画の回帰が自動検出できない。特に `InstancedMesh` のインスタンス行列は間違えても他の検証を素通りする
- 検討事項: E2E でのピクセル比較はソフトウェアWebGLの描画差で不安定になりやすい。`AntInstances.tsx` の行列書き込み関数を切り出し、`InstancedMesh` に対する単体テスト（未使用スロットが潰れていること、個体数が増減したときの整合）を書くほうが現実的
- 対応時期: **判断待ち**。Phase 4 でコロニー色とフェロモンのレンダラーが増え、描画の条件分岐が複雑になる前に入れておきたい

### イベントログが未実装

- 検出: Phase 2 / 統計パネル実装時
- 内容: 仕様書 §10「イベントログ」（コロニーの成立・消滅、系統の発生・絶滅、個体数の急増急減、全滅）が未実装。統計パネルは統計のみを表示している
- 判断: 記録対象6項目のうち4項目がコロニーと系統に関するもので、Phase 4 の実装が前提になる
- 対応時期: **Phase 4**（コロニー）。個体数の急増急減と全滅は Phase 2 の情報だけでも出せるが、ログ機構をPhase 4と二度作らないためまとめる

### `SimulationRuntime.getSpeed` が使われていない

- 検出: Phase 1 後 / ソース解説中に発見
- 内容: `src/state/simulationRuntime.ts` の `getSpeed` を呼んでいる箇所がない。再生速度は Zustand の `uiStore` が正本で、`SimulationDriver` が `setSpeed` で runtime へ流す一方向のため、読み返す必要がない
- 影響: なし。ただしインターフェースに未使用のメソッドが残る
- 対応時期: **Phase 5 の保存仕様を決めるとき**に判断する。保存対象に含めないなら削除する

### `framePriority.ts` の置き場所で state ↔ world が双方向依存になっている

- 検出: Phase 1 後 / ソース解説中に発見
- 内容: `FRAME_PRIORITY` が `src/world/renderers/` にあり、`state/SimulationDriver.tsx` がそれを参照している。一方 `world/renderers/*` は `state/simulationRuntime` と `state/uiStore` を参照しており、2つの層が相互に依存している
- 影響: 型と定数だけなので循環インポートにはならず、動作に問題はない。ただし依存の向きが一方向でないため、層の境界が曖昧になる
- 対応時期: **Phase 4 着手時**（コロニー・フェロモンのレンダラーが増え、priority を参照する箇所が増えるタイミング）
- 方針: `src/state/framePriority.ts` へ移動する。`world → state` の一方向に揃える

### 選択個体のカメラ追跡が未実装

- 検出: Phase 1 後 / ソース解説中に発見
- 内容: 仕様書 §9「選択個体を追跡する機能」、§10 個体詳細の「追跡開始、解除」が未実装
- 影響: 蟻は画面上で数ピクセルしかないため、選択しても目で追えない。Phase 2 で形質が見た目に出るようになり、個体を見比べる動機は増えた
- 対応時期: **Phase 4**（コロニー詳細でも対象を追う機能が要るため、共通の仕組みとして実装する）

### `prefers-reduced-motion` がカメラの慣性に効いていない

- 検出: Phase 1 後 / ソース解説中に発見
- 内容: 仕様書 §13「`prefers-reduced-motion` を尊重する」への対応が `app/index.css` のメディアクエリだけになっている。これは CSS のアニメーションとトランジションにしか効かず、`CameraRig.tsx` の `enableDamping`（JavaScriptによる慣性）は対象外
- 影響: 動きに敏感な利用者が設定を有効にしても、カメラの減速アニメーションは残る
- 対応時期: **Phase 5**（アクセシビリティ対応をまとめて行うPhase）
- 方針: `window.matchMedia('(prefers-reduced-motion: reduce)')` を参照し、有効なら `enableDamping` を false にする。設定変更の監視（`addEventListener('change')`）も行う

## 対応済み

### 蟻が餌の上に居座り、探索が起きなくなる可能性

- 検出: Phase 1 / バランス調整中
- Phase 2 での対応: 繁殖の導入で平衡点が変わったため、餌と代謝のバランスを全面的に再調整した。余剰エネルギーが繁殖に回り、個体数が増えると消費も増えるという負のフィードバックが働くようになり、Phase 1 のように供給過多で全個体が留まる状態にはなりにくい
- 現在の注意点は CLAUDE.md へ移した（餌を変更したときの確認事項）

### 未使用の定数・重複・型注釈漏れ（Phase 1 で記録した小さな負債）

- Phase 2 着手時にまとめて対応した
  - `config/world.ts` の `PHASE0_ANT_SPEED_MIN` / `PHASE0_ANT_SPEED_MAX` を削除
  - `FIELD_HALF - FIELD_MARGIN` の3重複を `FIELD_BOUND` へ集約
  - `distanceToNearestWater` に戻り値の型注釈を追加
  - `AntInstances.tsx` の重複インポートを1行へ
  - Phase 0 時点のまま古くなっていたコメントを現状に合わせた

### `generate.ts` と `movement.ts` に単体テストがない

- Phase 2 着手時に `generate.test.ts` と `movement.test.ts` を追加した
- 再生速度の線形補間、地形の重なり・境界、角度の正規化と旋回、進路が塞がれたときの挙動を検証している

### 「食べられる餌」の判定が2箇所に分かれている

- Phase 2 で `queries/worldStats.ts` が `isEdible` を使うようにした（当初の予定より前倒し）

### `InstancedMesh` の容量が初期個体数で固定されている

- Phase 2 で個体数上限（`MAX_POPULATION` = 500）ぶんを確保するようにした
- あわせて、毎フレーム容量ぶんを走査するのをやめ、生存個体ぶんだけ書き込むようにした

### 蟻の色に個体差がほとんど出ていなかった

- 検出: Phase 2 / 動作確認中（「蟻の色に違いはあるか」という指摘から計測して判明）
- 内容: 腹の色を「植物消化 - 肉消化」の差で緑↔赤へ補間していたが、-1〜+1 の全域を色域に割り当てていた。実際の形質差は ±0.2 程度しかないため、全個体が中間色（茶）になっていた。個体間の色差は255階調で11〜15しかなく、判別できなかった
- 対応: 食性ラベルの閾値（`DIET_THRESHOLD`）を基準に正規化し、「草食型」と判定される個体が緑、「肉食型」が赤として見えるようにした。あわせて緑と赤の彩度を上げ、体色の明度の幅も広げた
- 結果: 腹の色差が R 11→65、G 15→96（255階調）へ拡大。初期集団で赤・黄緑・茶が混在して見えるようになった
- 残る課題は「体格・視野・繁殖力の見た目の差が小さい」へ分離した
